Tracing an intrusion through network traffic

Only the network saw everything. From a single packet capture, the job is to follow the attacker from their first connection to the moment data left the network, without touching any endpoint.

Scenario

A company noticed unusual outbound traffic from its public web server late at night. The firewall team captured traffic on the server's network segment. No endpoint evidence was collected, so the packet capture is the whole story.

Questions to answer:

  • How did the attacker get into the web server?
  • Is there a command-and-control channel, and how does it behave?
  • Did the attacker reach other internal hosts?
  • What data left, and where did it go?

The Zeek logs were generated from a verified copy of the capture, so every finding traces back to the original packets.

Method

1. Turn packets into searchable logs

$ zeek -C -r capture.pcap
$ cat conn.log | zeek-cut id.orig_h id.resp_h id.resp_p duration orig_bytes resp_bytes | sort -k6 -nr | head

Sorting connections by bytes sent quickly shows which conversations moved the most data out.

2. Find the way in

# Wireshark display filter
http.request && ip.dst == 10.0.0.15
# Look for scanning, then a request that uploads or executes something

A burst of directory scanning is followed by a file upload to a vulnerable form, then requests to the uploaded web shell.

3. Spot the command-and-control beacon

$ cat conn.log | zeek-cut ts id.resp_h id.resp_p | grep 203.0.113.99
# Regular intervals with small, similar sizes = beaconing

The server calls out to the same address every 60 seconds with near-identical packet sizes, which is the signature of an automated beacon.

4. Follow lateral movement and recover what left

# Wireshark display filters
smb2 || rdp || tcp.port == 5985
dns.qry.name contains "sample-exfil"
# NetworkMiner: extract transferred files and compare hashes

SMB connections from the web server to an internal file server, then long, encoded DNS queries, show data being smuggled out a few bytes at a time.

Lessons

  • Validate and restrict file uploads, and never let uploaded files execute.
  • Separate public servers from internal file shares so one compromise can't reach both.
  • Watch for beaconing patterns and unusually long DNS queries; both are easy to alert on.
  • Network evidence alone can tell the full story when endpoints aren't available.
